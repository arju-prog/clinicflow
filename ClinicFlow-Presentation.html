STAGE 01 · APPLICATION

The working app

Without a working application, no DevOps layer means anything. This is the foundation everything else carries.

  • FastAPI backend, 8+ REST endpoints across doctors, patients, appointments
  • PostgreSQL with Alembic migrations — schema as versioned code
  • /health, /ready, /metrics endpoints
  • Responsive React UI — a real dashboard, not a blank page

WHY TWO HEALTH ENDPOINTS?

/health — liveness

"Is the process up?" No database call, so a DB blip never restarts every pod at once.

/ready — readiness

"Can it serve traffic now?" Checks the database first — returns 503 until it answers.

STAGE 03 · CI PIPELINE

GitHub Actions — the automation backbone

Runs on every push to main. Tests are the first quality gate: if they fail, no image is ever built or deployed.

1 · TEST

ruff + 36 pytest tests, Vitest, helm lint, terraform validate, secret scan

→

2 · BUILD + SCAN + PUSH

Build both images → Trivy scan → push to GHCR, tagged with the Git SHA

→

3 · DEPLOY

helm upgrade --install to EKS, keyless via GitHub OIDC

✅

Quality gate: a failing test exits non-zero → the build stops → no broken image is ever promoted to production.

  • docker compose up --build starts all three services

STAGE 05 · SECURITY SCAN

Trivy — a gate, not a guarantee

The pipeline scans both images and fails the build on any fixable HIGH or CRITICAL vulnerability. A vulnerable image is never pushed.

THE PROBLEM IT CAUGHT

First scan failed: 4 HIGH CVEs (urllib3, msgpack, setuptools) — all bundled inside pip, which ClinicFlow never uses.

THE FIX

Removed pip from the runtime image. All four CVEs gone, smaller attack surface. Result: 0 HIGH/CRITICAL.

STAGE 06 · REGISTRY

Published to GHCR

The pipeline pushes both images to the GitHub Container Registry — tagged with the exact Git commit SHA, never latest.

Why the SHA, not latest?

Full traceability: any running pod points back to the exact commit that built it. Rollback = redeploy an older SHA.

STAGE 08 · KUBERNETES

Running in the cluster

Deployments keep pods alive; Services give them stable networking even as pods come and go.

  • Backend + frontend, 2 replicas each, spread across nodes
  • ClusterIP Services for stable internal routing
  • PostgreSQL as a StatefulSet with an EBS volume
  • Hardened pods: non-root, read-only FS, dropped capabilities

STAGE 13 · TROUBLESHOOTING

Breaking it on purpose

Deliberately broken manifests, each teaching one failure mode and how to diagnose it with kubectl.

ImagePullBackOff

Wrong image tag → describe pod reveals it in Events

Service, no endpoints

Selector typo → no matching labels → no traffic. Labels are the only link.

CrashLoopBackOff

Bad DB config → logs + readiness never passes

REAL PROBLEMS I SOLVED

Not a tutorial — real engineering

🛡 Supply-chain awareness

Pinned the Trivy action to a commit SHA — its version tags were hijacked in a March 2026 attack.

☁️ AWS Free-plan limits

t3.medium was blocked — switched the node group to Free-Tier m7i-flex.large.

🔑 OIDC trust debugging

GitHub's new ID-based tokens broke the deploy role — fixed the IAM trust policy to accept them.

🧩 Removing > upgrading

Dropped pip from the runtime image — cleared 4 HIGH CVEs and shrank the attack surface.
