# Security in the ClinicFlow pipeline

## Trivy: what was scanned and what the result means (M6 write-up)

On every pipeline run Trivy scans both container images: the operating-system packages (Debian 13 in the backend, Alpine 3.24 in the frontend) and every application library inside them (the Python packages in the backend's virtualenv and the packages bundled in the base image). Trivy matches each package version against public vulnerability databases. The gate fails the build on any **HIGH or CRITICAL** CVE **that has a fix available** (`ignore-unfixed: true`), so we only block on problems we can actually act on. The current result is **0 HIGH/CRITICAL** for both images. That doesn't mean the images are "secure"; it means that no *known, fixable* serious vulnerability exists in their packages today.

### The CVE we found and fixed

The first local scan of the backend image failed with four HIGH findings:

| Package | CVE / advisory | Fixed in | Where it came from |
|---|---|---|---|
| urllib3 2.7.0 | CVE-2026-97687: traffic interception via HTTPS proxy TLS configuration override | 2.8.0 | copy vendored *inside pip* |
| urllib3 2.7.0 | CVE-2026-97689: denial of service via unbounded memory allocation in the chunk parser | 2.8.0 | copy vendored inside pip |
| msgpack 1.1.2 | GHSA-6v7p-g79w-8964: out-of-bounds read on Unpacker reuse | 1.2.1 | vendored inside pip |
| setuptools 70.3.0 | CVE-2025-47273: path traversal in PackageIndex | 78.1.1 | bundled with the python base image |

ClinicFlow never imports any of these. They existed only because **pip** (and its vendored dependencies) shipped in the image. pip is only needed at *build* time, so the Dockerfile now uninstalls it from the runtime stage. All four findings disappeared, and the image has less attack surface. The lesson: the best fix is often *removing* what you don't need, not upgrading it.

## Security layers

| Layer | What ClinicFlow does | Where |
|---|---|---|
| Secret scanning | Trivy `fs --scanners secret` fails CI if credentials are committed; `.env`/`*.tfvars` are git-ignored | `ci-cd.yml` → `secret-scan` |
| Dependency scanning | Trivy scans the Python/npm packages baked into each image | `ci-cd.yml` → Trivy gate |
| Container scanning | OS + library CVEs, HIGH/CRITICAL fail the job; full report uploaded as SARIF to *Security → Code scanning* | `ci-cd.yml` |
| IaC scanning | Trivy `config` reports Terraform/Helm/Dockerfile misconfigurations (report-only) | `ci-cd.yml` → `secret-scan` |
| Supply chain | third-party action `trivy-action` pinned to a commit SHA (its tags were hijacked in March 2026); the image that is pushed is byte-for-byte the one that was scanned | `ci-cd.yml` |
| Least privilege (cloud) | GitHub → AWS via OIDC, trusted only for this repo's `main`/`production`; the role can only `eks:DescribeCluster` in AWS | `terraform/github-oidc.tf` |
| Least privilege (pods) | non-root users, read-only root filesystem, `drop: [ALL]` capabilities, `seccomp: RuntimeDefault`, Pod Security Admission (`baseline` enforced, `restricted` warned) | Helm templates, `k8s/namespace.yaml` |
| Network | NetworkPolicy: only backend pods may connect to PostgreSQL | `templates/networkpolicy.yaml` |
| Secrets at runtime | Postgres password generated by Helm, kept in a Secret, injected via `secretKeyRef`, never in the Deployment spec | `templates/secret.yaml` |
| Runtime security | *not implemented*; a tool like Falco would detect suspicious behaviour inside running containers | — |

## Known, accepted findings

`trivy config` reports these on purpose:

- **EKS public API endpoint** (`AVD-AWS-0040`): needed so GitHub-hosted runners and a laptop can reach the cluster. Production would restrict `endpoint_public_access_cidrs` or use private runners.
- **Unrestricted node egress**: worker nodes need to pull images from GHCR and Docker Hub.
- **`troubleshooting/*.yaml`**: intentionally broken lab manifests.
